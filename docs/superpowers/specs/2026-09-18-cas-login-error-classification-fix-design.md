# CAS 密码登录错误分类修正设计

## 问题

学校 CAS 在密码错误和账号锁定时都返回 HTTP 200，真实错误文本位于 `<span id="msg1">`。当前实现却匹配 `id="msg"`，并在读取错误节点前扫描整页 HTML 中的 `disabled`、`禁用` 等宽泛关键词。登录页自身的控件或脚本可能包含这些词，导致普通的“账号或密码错误”被误判为账号锁定。

## 修正方案

- 后端先从 CAS 明确的错误消息节点提取文本，同时兼容 `msg1` 和旧的 `msg`，允许属性顺序及单、双引号变化，并去除节点内简单 HTML 后得到可判断文本。
- 只根据提取出的错误文本判断账号锁定：包含“账号被锁定”“锁定”“冻结”等明确语义时返回 `ACCOUNT_LOCKED`。不再用整页中的 `disabled` 或“禁用”判断账号状态。
- 验证码仍使用页面中真实 `authcode` 输入字段作为 `CAPTCHA_REQUIRED` 判断依据。
- 错误文本包含“账号或密码错误”“密码错误”“不正确”“不存在”“无效”时返回 `WRONG_PASSWORD`；无法识别时返回 `OTHER_ERROR` 并保留学校返回的文本。
- `UserServiceImpl` 对 `WRONG_PASSWORD` 返回稳定、直接的业务提示 `账号或密码错误`；真实锁定继续返回 `学号已被学校系统锁定，请稍后再试或改用短信/扫码`。

## 接口结果

项目现有统一异常结构保持不变，两类失败的 HTTP 状态仍为 200、JSON `code` 仍为 666，只通过 `message` 区分：

- 密码错误：`账号或密码错误`
- 账号锁定：`学号已被学校系统锁定，请稍后再试或改用短信/扫码`

验证码流程保持 JSON `code: 1004`，本次不修改前端和其他登录方式。

## 验证

增加后端针对典型 CAS HTML 片段的分类验证，至少覆盖：普通页面含 `disabled` 但 `msg1` 为密码错误、真实锁定、验证码激活、未知错误。随后执行后端编译或打包（跳过测试）；不进行浏览器自动化。
